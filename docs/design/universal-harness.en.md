## Goal

Attestflow is a reusable development harness. It lets projects adopt one controlled development workflow instead of copying a one-off scaffold from a business repository.

The harness is not a test framework. It is a development control system that makes this chain explicit, repeatable, resumable, and auditable:

```text
requirement source -> draft spec -> clarification -> approved spec -> AI planning -> task import
-> requirement boundary -> BDD scenario -> unit test -> implementation
-> verification -> evidence -> task state transition -> next executable task
```

Raw sources can only create draft specs, not ready tasks. Only an approved spec can enter AI planning; planner JSON still has to pass deterministic `task import` validation before autopilot or dispatch can run it.

The core principle is AI-first generation with deterministic orchestration. Programming agents own goal decomposition, task drafts, BDD, and acceptance criteria. Attestflow owns validation, ID allocation, state, locks, verification, and evidence.

## Non-goals

- Do not implement business product logic in this repository.
- Do not hard-code Python, Node, Go, Rust, or any other stack into the protocol core.
- Do not require a specific external agent, private workflow, GitHub, Docker, or CI platform.
- Do not let agent orchestration bypass task state, file ownership, or evidence gates.
- Do not use conversation memory as the source of truth for task state or recovery.
- Do not make hand-written task files the main path; runtime tasks are JSON files written by Attestflow.

## Design Principles

1. Protocol first: task schema, state transitions, gates, evidence, locks, and run ledger are stable interfaces.
2. AI first: planning, task drafts, BDD, acceptance, and file scopes are generated by programming agents by default.
3. Deterministic persistence: agents emit planner JSON; Attestflow assigns IDs, fills defaults, validates schema, and writes runtime task JSON.
4. Adapters second: languages, test commands, CI platforms, issue systems, Docker, and routing live in project config.
5. No executable proof, no implementation: BDD before unit tests before implementation.
6. No fresh evidence, no completion: `done` must cite the current run evidence.
7. Recover from files, not memory.
8. One task, one independent agent session.
9. Parallelism requires write ownership.
10. Default conservative behavior: unclear requirements go to `needs_clarification`; missing external inputs go to `blocked`.

## Repository Shape

The core implementation keeps standard-library-first code for config, planner import, task validation, task selection, capability execution, top-level autopilot, PR/CI/release providers, evidence, recovery, secret scanning, adapters, templates, and tests.

Target projects receive a `harness.yml`, task directories, gates, agent role docs, adapter docs, and runtime evidence directories.

## `harness.yml`

Every onboarded project has a `harness.yml` with these concerns:

- `project`: name, default branch, adapter, and `language`.
- `paths`: task, run, gate, lock, capability, autopilot, CI, Git, PR, release, plugin, source, and docs paths.
- `commands`: BDD, unit, lint, typecheck, secret scan, and project verify commands.
- `policies`: DoR/DoD, BDD-before-unit, unit-before-implementation, fresh verify, agent sessions, write scopes, linked issue triage, and Docker policy.
- `security`: provider command allowlist, output limits, approval policy, environment policy, network signal, and filesystem mode.
- `sessions`: agent provider, launch/resume command, provider options, and optional worktree isolation.
- `autopilot`: repair attempts, default batch size, step budget, loop policy, and resource budgets.
- `capabilities`: intake, planner, BDD, TDD, implementer, reviewer, verifier, and releaser provider routing.
- `context` and `token_economy`: bounded repository context, summaries, caches, incremental context, dynamic context requests, and evidence summaries.
- `integrations`: Git, CI, PR, and release providers.
- `plugins` and `policy_packs`: local extension discovery.

Core code reads configuration; it does not infer behavior from historical projects or private tool names.

## Capabilities

Attestflow does not depend on external skills, but it adopts the useful structure of skill systems. Each capability declares name, specialist, phase, inputs, outputs, gates, evidence, provider, and whether it has external dependencies.

Built-in capabilities:

```text
intake       requirements partner
planner      spec planner
bdd          behavior spec author
tdd          test engineer
implementer  implementation worker
reviewer     staff engineer reviewer
verifier     verification lead
releaser     release engineer
```

`capability list/show` displays contracts. `plan` runs a goal-level planner capability. `capability run <name> <task>` runs a task-level capability. Codex, Claude Code, OpenCode, external skills, and custom agent CLIs connect through provider adapters rather than becoming core dependencies.

## Repository Context

Provider input includes deterministic repository context:

- bounded file tree
- configured documents
- task focus files from `files.read` and `files.write`
- dynamic context affordances such as file slices, symbol lookup, dependency neighbors, semantic search, change history, and test mapping
- actual limits used for context collection

Token economy controls replace oversized content with summaries, content hashes, cache keys, and retrieval hints. Providers request additional slices through dynamic context instead of scanning the repository themselves.

## Task Storage and State Machine

Runtime tasks are JSON files under configured state directories:

```text
harness/tasks/
  proposed/
  needs_clarification/
  ready/
  in_progress/
  blocked/
  review/
  verified/
  accepted/
  done/
  archived/
```

Directory state and the task `state` field must match. The scheduler computes order from dependencies, readiness, locks, write scopes, priority, and ID. Invalid transitions fail closed; direct shortcuts such as `ready -> done` are forbidden.

## Gates and Blockers

Definition of Ready requires purpose, scope, out-of-scope, no unresolved executable placeholders, BDD scenarios, unit tests, acceptance criteria, satisfied dependencies, declared write files, and satisfied external inputs.

Definition of Done requires passing BDD/unit/project verification where applicable, lint/typecheck where applicable, docs/changelog handling, linked issue handling, secret scan, current-run evidence, and legal final state transition.

Blockers are structured state, not free-form notes. `blocked` tasks must contain active blockers with reason, unblock condition, owner, source, status, and timestamps. `unblock` resolves blockers one by one; only when all active blockers are resolved can a task return to `ready`.

## CLI Surface

Stable commands include:

- `init`: generate base files and adapter docs, write `project.adapter`, `project.language`, and selected provider presets.
- `doctor`: check config, commands, runtime layout, task schema, provider CLI, and provider preflight.
- `validate-config`, `validate-task`, `task import`, `source import`, `schema migrate/export/openapi`, `plugin list`, `governance policy`.
- `tasks`, `next`, `autopilot --dry-run`, `autopilot --run`, `autopilot --resume`, `autopilot --loop`, `autopilot --status`.
- `inspect --run`, `inspect --diff`, `recover`, `dispatch`, `start`, `block`, `unblock`.
- `evidence`, `evidence export`, `evidence bundle`, `evidence verify`, `contract validate`, `provider contract`.
- `verify`, `verify --task`, `ci`, `pr`, `release`, `close`, `resume`, `secret-scan`.

## CI, PR, and Release Providers

CI providers use contracts like programming agent providers. `github-actions` is an adapter that maps `gh` output to the unified CI contract; command providers can connect other CI systems.

PR providers create, update, merge, and query external change requests. Autopilot ensures PR evidence during the accepted stage and can auto-merge only when `integrations.pr_provider.auto_merge: true` is explicitly configured and CI has passed.

Release providers collect external release status after all tasks are done or archived. `released` and `skipped` are converged states; `running`, `queued`, and `unknown` pause for resume; `failed` can trigger repair planning when a planner capability is configured.

## Runs, Evidence, and Recovery

Every task execution writes a run directory with metadata, ledger, prompt/session packet, command results, capability evidence, and close evidence. `ledger.jsonl` is append-only and hash-chained.

`resume` must answer current task, state, lock, last event, recent successful gate, recent failed gate, next action, and whether continuation is possible. Ambiguous recovery returns non-zero instead of guessing.

## Multi-agent Orchestration

Agent roles are protocol roles, not business identities. Parallel execution is allowed only when each agent has a task id, a declared write set, disjoint write scopes, locked shared files, and its own evidence. Otherwise tasks run sequentially.

## Project Adapters

Adapters provide default files and command detection without changing the core protocol:

- `generic`: standard directories and project-provided commands.
- `python`: unittest defaults plus optional pytest, ruff, and mypy detection.
- `node` and `monorepo`: package manager and package script mapping.
- `go`, `rust`, `docker`, `bazel`, `java`, `kotlin`, `dotnet`, `swift`, `dart`, `ruby`, and `php`: standard project file detection and baseline verification commands.

Adapter-generated files can be edited by the project; `harness.yml` remains the source of truth.

## Onboarding Flow

1. Run the one-command bootstrap or `python -m attestflow init --adapter <adapter> --language en|zh-CN --agent-provider <provider>`.
2. Run `python -m attestflow doctor`.
3. Have the programming agent review generated config and project commands.
4. Generate planner JSON from the goal and repository context.
5. Run `python -m attestflow task import --from-json plan.json`.
6. Audit execution with `autopilot --dry-run`.
7. Run `autopilot --run` or `dispatch`.
8. Let capabilities advance BDD, unit tests, implementation, review, verification, PR/CI gates, close, and release evidence.

## Acceptance Criteria

- Core protocol and project adapters stay separated.
- The harness preserves requirement convergence, BDD/TDD, state transitions, evidence, and recovery.
- State transitions, gates, evidence, recovery, and multi-agent ownership are explicit.
- The core does not hard-depend on historical projects, external agent tools, Docker, GitHub, or Python-only workflows.
- The design can drive implementation without guessing the main behavior.
